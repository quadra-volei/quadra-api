# Spec: F2.2 — Player Card (data)

## Origin
- User Story / Feature from SCOPE: F2.2 — Player Card (data)
- Layer: 2
- Requested by: renanortega.dev@gmail.com

## Goal
Expose a single "player card" endpoint that returns the JSON data behind a FIFA-style card — stats, level, positions and a free/premium flag — generated once a player has 3 recorded matches, so the app has one authoritative payload to render a card that F2.1's separate profile/stats/history endpoints did not provide as a unit.

## Primary module
`Quadra.Modules.Profile`

> Rationale: SCOPE lists F2.2 as `Profile (data) + Gamification (premium check)`. The **card data** (the `player_cards` own table listed for the Profile module in ARCHITECTURE, its generation gate and its read endpoints) is the protagonist and lives in `Profile`. `Gamification` contributes only a boolean read (`premium check`) via a `Quadra.Shared.Contracts` interface — a dependent, not a co-protagonist — so this stays a single-primary-module spec. Card generation is performed asynchronously by `Quadra.Workers.Background` on the same `MatchSummaryGenerated` signal already consumed for F2.1; the Worker invokes a Profile-owned write path (it is transport, not a co-author).

## Dependent modules (read-only via interface)
- `Quadra.Modules.Gamification` — the `premium check`. A new `IPremiumStatusReader` (declared in `Quadra.Shared.Contracts`, implemented in Gamification) answers `IsPremiumAsync(userId)`. See Open questions #1 — in the MVP this is a stub returning `false` (no billing per PRODUCT); the persistent premium data structure is out of scope until billing is specified.
- `Quadra.Modules.Auth` — the FA.1 JWT middleware populates `HttpContext.User` with the caller's `sub`; the `GET /card` endpoints read the claim, never the `users` table.

Profile holds **no** `ProjectReference` to `Gamification`. The premium read is reached exclusively through the `Quadra.Shared.Contracts` interface, resolved via DI in the API host. Profile touches only its own tables (`player_cards`, plus the F2.1 `player_profiles` / `player_stats` it already owns).

## Database changes

### New tables

#### `player_cards`
Realizes the `player_cards` own table listed for the Profile module in ARCHITECTURE. One row per player, created (generated) the first time the player crosses 3 recorded matches and refreshed on every subsequent finished match. It is a materialized snapshot of the card's static display fields; the dynamic premium flag is resolved at read time and is **not** stored here.
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` `uuid` `NOT NULL UNIQUE` — app-layer FK to `users.id`; no DDL FK (module boundary rule). One card per user.
- `display_name` `varchar(80)` `NOT NULL` — snapshot of `player_profiles.display_name` at (re)generation
- `primary_position` `varchar(24)` `NULL` — snapshot; enum string `Setter | OutsideHitter | Opposite | MiddleBlocker | Libero`
- `secondary_position` `varchar(24)` `NULL` — snapshot; same enum
- `level` `varchar(16)` `NOT NULL` — snapshot of the derived `player_profiles.level` (MVP: `Beginner | Intermediate`)
- `matches_played` `integer` `NOT NULL` — snapshot of `player_stats.matches_played`
- `wins` `integer` `NOT NULL`
- `losses` `integer` `NOT NULL`
- `draws` `integer` `NOT NULL`
- `mvps_received` `integer` `NOT NULL`
- `generated_at` `timestamptz` `NOT NULL` — when the card was first generated (the 3rd-match crossing). Set once, never overwritten on refresh.
- `refreshed_at` `timestamptz` `NOT NULL` — last snapshot refresh
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`

**Indexes:** unique btree on `user_id`.

> No `premium`/`plan` column — the free/premium flag is resolved live via `IPremiumStatusReader` at read time (it can change independently of card generation and, in the MVP, has no persistent source; see Open questions #1). Storing it would create stale data.

### New columns in existing tables
None.

### Migrations required
- `<TimestampPrefix>_CreatePlayerCardsTable` — generated under `src/Quadra.Modules.Profile/Migrations/` (EF generates the rollback).

## REST endpoints

### `GET /api/v1/profiles/me/card`
Returns the authenticated caller's own player card.
- **Auth**: JWT required (`[Authorize]`)
- **Request**: no body
- **Response 200 OK**: `PlayerCardResponse` (see below)
- **Possible errors**:
  - `401` — missing or invalid JWT
  - `404` — no profile exists for the caller
  - `409` — profile exists but the card has not been generated yet (fewer than 3 recorded matches)
- **Behavior**:
  1. Extract `callerId` from `User.FindFirst(ClaimTypes.NameIdentifier)?.Value`; return `401` if parse fails.
  2. Load the card via `IPlayerCardRepository.FindByUserIdAsync(callerId, ct)`.
     - If a profile does not exist for the caller → `404` (`ProfileNotFoundException`).
     - If a profile exists but no `player_cards` row exists → `409` (`CardNotGeneratedException`, carries `MatchesPlayed` and the threshold `3`).
  3. Resolve the premium flag: `isPremium = await IPremiumStatusReader.IsPremiumAsync(callerId, ct)`.
  4. Map the snapshot + `isPremium` → `PlayerCardResponse` → `200 OK`.

### `GET /api/v1/profiles/{userId}/card`
Returns another player's card (public within the app — a card carries no private fields).
- **Auth**: JWT required (`[Authorize]`)
- **Request**: no body
- **Response 200 OK**: `PlayerCardResponse`
- **Possible errors**:
  - `401` — missing or invalid JWT
  - `404` — no profile exists for `userId`
  - `409` — profile exists but the card has not been generated yet
- **Behavior**: identical to `GET /profiles/me/card` but keyed on route `userId`.

### Response records
```csharp
public sealed record PlayerCardResponse(
    Guid UserId,
    string DisplayName,
    string? PrimaryPosition,
    string? SecondaryPosition,
    string Level,                       // MVP: Beginner | Intermediate
    PlayerStatsResponse Stats,          // reuses the existing F2.1 record
    bool IsPremium,                     // resolved live via IPremiumStatusReader; MVP stub → false
    DateTimeOffset GeneratedAt,
    DateTimeOffset RefreshedAt);
```
`PlayerStatsResponse` is the existing F2.1 record (`MatchesPlayed, Wins, Losses, Draws, MvpsReceived`) — reused, not duplicated.

## SQS events

### Published
None. Profile publishes nothing in the MVP.

### Consumed
No **new** SQS consumer. Card generation piggybacks on the F2.1 consumption of `MatchSummaryGenerated` (from `Quadra.Modules.Matches`, F1.6) inside `Quadra.Workers.Background`. That existing consumer already invokes the Profile-owned `IPlayerStatsWriter.ApplyFinishedMatchAsync(...)`; this spec **extends that same write path** (`ApplyFinishedMatchHandler`) to (re)generate the card in the same transaction. No change to `MatchSummaryGeneratedProfileConsumer` is required — the consumer's contract is unchanged; only the Profile handler it calls gains a card-write step.

> `MvpAwarded` and other per-match events are **not** consumed for the card — the card is derived from the recomputed `player_stats`/`player_profiles` written by the single authoritative `MatchSummaryGenerated` path (avoids double counting, consistent with F2.1).

- **Visual rendering / card image generation** — frontend; this spec returns JSON only (SCOPE OUT).
- **Premium art variants / cosmetic catalog** — SCOPE OUT ("catalog comes later").
- **Billing, subscription, payment or the persistent premium data structure** — PRODUCT states monetization is validation-only with no MVP implementation; the MVP resolves the flag via a stub returning `false`. No `plan`/`premium` column or table is created here (see Open questions #1).
- **Card for players with fewer than 3 recorded matches** — no `player_cards` row exists; the read endpoints return `409`.
- **Manual editing of card fields** — everything is derived from `player_profiles`/`player_stats`, themselves derived from `MatchSummaryGenerated` (consistent with F2.1 OUT: manual stat editing).
- **A new SQS consumer or new event** — card generation reuses the F2.1 `MatchSummaryGenerated` path.
- **City-wide / group ranking on the card** — F2.3 and Layer 3; the card shows no point totals or ranking.
- **Advanced/Elite level tiers** — deferred (F2.1); the card mirrors the two MVP tiers.

## Implementation notes
- **Snapshot vs live**: `player_cards` stores the static display fields as a snapshot refreshed on every finished match, so a read is always current as of the player's last match. The premium flag is the only field resolved live (at read time), because it can change independently of match play and, in the MVP, has no persisted source.
- **Generation gate**: `PlayerCard.GenerationThreshold = 3`. `ApplyFinishedMatchHandler` writes the card only when `matches_played >= 3`; `generated_at` is set once (first crossing) and preserved across refreshes, `refreshed_at` updated each time.
- **Idempotency**: card upsert keys on `user_id`; because stats are recomputed-not-incremented (F2.1), a redelivered `MatchSummaryGenerated` reproduces the identical snapshot — no drift.
- **`409` semantics**: `GetPlayerCardHandler` distinguishes "no profile" (`404`) from "profile exists, card not yet generated" (`409`), so the client can tell a non-existent player apart from a new player who has not reached 3 matches. `CardNotGeneratedException` carries `MatchesPlayed` and `3` for a helpful ProblemDetails body.
- **CancellationToken** propagated through every handler, repository, reader and the extended write path (sourced from `HttpContext.RequestAborted` in the API, the stopping token in the Worker).
- **TimeProvider**: reuse the `TimeProvider` already registered by `AddProfileModule`; `generated_at`/`refreshed_at` come from `GetUtcNow()` so tests control time.
- **Controller thinness**: the two new actions only extract the claim, call the handler and map exceptions to ProblemDetails — no business logic.
- **Serilog**: log `UserId` and `IsPremium` at `Information` on a card read; never log at a level that would expose another player's data beyond the requested `userId`.
- **Nullable reference types** enabled; nullable card fields are exactly `primary_position` and `secondary_position`.
