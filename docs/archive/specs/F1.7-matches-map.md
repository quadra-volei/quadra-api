# Spec: F1.7 — Matches Map

## Origin
- User Story / Feature from SCOPE: F1.7 — Matches Map
- Layer: 1 (Match Core)
- Requested by: Renan Johny Ortega

## Goal
Enable an authenticated player to discover nearby matches that still have open slots — via a PostGIS radius query — so DropIns can find sessions to join without relying on WhatsApp.

## Primary module
`Quadra.Modules.Geo`

> Rationale for a single primary module: SCOPE lists F1.7 under `Geo`. Per `ARCHITECTURE.md`, the Geo module "owns nothing — only runs geographic queries over the matches tables" and holds the explicit **exception to the boundary rule**: read-only SELECT permission on `matches`. This spec therefore places the PostGIS `ST_DWithin` query inside Geo (over a read-only view of `matches`) and obtains slot-occupancy — which lives in the Matches-owned `match_presences` table — through a cross-module interface exposed by `Matches`. No new tables are introduced; the spatial column and GIST index were already provisioned by F1.1 in anticipation of this feature.

## Dependent modules (read-only via interface)
- `Quadra.Modules.Matches` — to obtain per-match slot occupancy ("does this match still have open slots / open DropIn slots?"). Occupancy is derived from `match_presences` (owned by Matches). Geo consumes a new `IMatchAvailabilityReader` interface declared in `Quadra.Shared.Contracts` and implemented in `Quadra.Modules.Matches`. Geo does **not** read `match_presences` directly (that table is outside its sanctioned SELECT grant), and there is no cross-module JOIN — the spatial candidates and their occupancy are combined in application code.
- `Quadra.Modules.Auth` — the FA.1 JWT middleware populates `HttpContext.User` with the caller's `sub`; Geo reads the claim to authorize the request. It never queries the `users` table.

## REST endpoints

### `GET /api/v1/matches/nearby?lat={double}&lon={double}&radiusKm={double}&openToDropIns={bool}`
Returns upcoming matches within `radiusKm` of the given point that still have at least one open slot, ordered by distance ascending.
- **Auth**: JWT required (`[Authorize]`)
- **Request** (query parameters):
  ```csharp
  public sealed record NearbyMatchesQuery(
      double Lat,
      double Lon,
      double RadiusKm,
      bool OpenToDropIns = false);
  ```
- **Response 200 OK**:
  ```csharp
  public sealed record NearbyMatchesResponse(
      IReadOnlyList<NearbyMatchResponse> Items,   // ordered by DistanceKm ascending
      int Count);

  public sealed record NearbyMatchResponse(
      Guid Id,
      string Name,
      string Address,
      double Latitude,
      double Longitude,
      double DistanceKm,               // straight-line distance from the query point, 3 decimals
      DateTimeOffset DateTime,
      int MaxPlayers,
      int OpenSlots,                   // Math.Max(0, MaxPlayers - ConfirmedCount)
      bool OpenToDropIns,              // a DropIn can still join per Matches slot rules
      decimal? Price,
      string Type,                     // Recurring | OneOff
      string Status);                  // Open | Closed
  ```
- **Possible errors**:
  - `400` — invalid query params (see Validation)
  - `401` — missing or invalid JWT
- **Validation** (`NearbyMatchesQueryValidator`, FluentValidation):
  - `Lat`: range `[-90, 90]`
  - `Lon`: range `[-180, 180]`
  - `RadiusKm`: `> 0` and `<= 50`
  - `OpenToDropIns`: optional; defaults to `false`
- **Behavior**:
  1. Extract `callerId` from `User.FindFirst(ClaimTypes.NameIdentifier)?.Value`; return `401` if parse fails.
  2. Run `NearbyMatchesQueryValidator`; return `400 ValidationProblem` on failure.
  3. Build the query point `new Point(Lon, Lat) { SRID = 4326 }` (PostGIS convention: X = longitude, Y = latitude).
  4. Query the Geo-owned read-only `matches` view via `INearbyMatchRepository.FindWithinRadiusAsync(point, radiusKm, now, cancellationToken)`:
     - filter `ST_DWithin(location, point, radiusKm * 1000)` (geography → meters), expressed in EF as `m.Location.IsWithinDistance(point, radiusMeters)`;
     - filter `status IN ('Open', 'Closed')` (the only states in which a match is joinable);
     - filter `date_time > now` (upcoming only; `now = TimeProvider.GetUtcNow()`);
     - project `Id`, `Name`, `Address`, `Latitude` (`location.Y`), `Longitude` (`location.X`), `DateTime`, `MaxPlayers`, `Price`, `Type`, `Status`, and `DistanceMeters = m.Location.Distance(point)`;
     - order by `DistanceMeters` ascending;
     - cap at a fixed upper bound (200 rows) to keep the response bounded — see Implementation notes.
  5. If no candidates → return `200 OK` with `Items = []`, `Count = 0`.
  6. Call `IMatchAvailabilityReader.GetAvailabilityAsync(candidateIds, cancellationToken)` (implemented by Matches) to obtain `OpenSlots` and `HasOpenDropInSlot` per candidate match.
  7. Keep only candidates with `OpenSlots > 0` ("matches with open slots"). If `OpenToDropIns == true`, additionally keep only those with `HasOpenDropInSlot == true`.
  8. Map each surviving candidate → `NearbyMatchResponse` (`DistanceKm = Math.Round(DistanceMeters / 1000, 3)`; `OpenSlots` and `OpenToDropIns` taken from the availability reader), preserving distance-ascending order.
  9. Return `200 OK` with the assembled `NearbyMatchesResponse`.

## Acceptance criteria (from SCOPE)
- [ ] **`GET /matches/nearby?lat&lon&radiusKm` endpoint — returns matches with open slots**: `GET /api/v1/matches/nearby?lat=..&lon=..&radiusKm=..` by an authenticated caller returns `200` with matches within the radius whose `OpenSlots > 0`, ordered by `DistanceKm` ascending; matches with no open slots are excluded from `Items`.
- [ ] **filter by matches open to DropIns**: the same endpoint with `openToDropIns=true` returns only matches for which a DropIn can still join (`OpenToDropIns == true`); with `openToDropIns=false` (default) it returns all matches with open slots regardless of DropIn availability.
- [ ] **PostGIS query (ST_DWithin on `geography` with SRID 4326)**: the radius filter is implemented as `ST_DWithin(location, ST_SetSRID(ST_Point(lon, lat), 4326)::geography, radiusKm * 1000)` over the `matches.location` `geography(Point, 4326)` column, backed by the existing `ix_matches_location_gist` GIST index; a match exactly outside the radius is excluded and one inside is included.

## Out of scope (be explicit)
- **court/arena pins (Layer 3)** — explicitly OUT per SCOPE F1.7; this endpoint returns matches only, never venue/court entities.
- **routes / directions** — explicitly OUT per SCOPE F1.7; the response carries a straight-line `DistanceKm`, no routing/ETA.
- **Pagination / cursoring** — SCOPE requests a radius query, not a paged list. Results are bounded by `radiusKm` and a fixed cap (see notes); no `page`/`pageSize` params.
- **Writing to or mutating `matches`** — Geo is read-only; it neither owns nor migrates any table.
- **Slot-release / DropIn eligibility rules** — the authoritative "can a DropIn join?" logic lives in Matches (F1.1/F1.2); Geo only consumes the computed `HasOpenDropInSlot` flag. This spec does not redefine those rules.
- **Reading `match_presences` from Geo** — occupancy comes exclusively through `IMatchAvailabilityReader`; Geo never touches presence tables directly.
- **Player search by level / position / region, GPS-based recommendations** — Layer 3, REJECTED.
- **Real-time updates of the map** — no SignalR; the map is pull-based.

## Implementation notes
- **`IMatchAvailabilityReader` shape** (declared in `Quadra.Shared.Contracts`, implemented in `Quadra.Modules.Matches`):
  ```csharp
  public interface IMatchAvailabilityReader
  {
      // Returns availability for the requested match IDs; IDs with no match are omitted from the dictionary.
      Task<IReadOnlyDictionary<Guid, MatchAvailability>> GetAvailabilityAsync(
          IReadOnlyCollection<Guid> matchIds,
          CancellationToken cancellationToken);
  }

  public sealed record MatchAvailability(
      Guid MatchId,
      int MaxPlayers,
      int ConfirmedCount,        // confirmed presences (Regular + DropIn)
      int OpenSlots,             // Math.Max(0, MaxPlayers - ConfirmedCount)
      bool HasOpenDropInSlot);   // true when a DropIn can still be confirmed per Matches slot rules
  ```
  This mirrors the existing cross-module read pattern (`IMatchReader`, `IConfirmedPlayersReader` — Matches side; `IMatchResultReader` — InGame side). No project reference from Geo to Matches: the interface is resolved via DI.
- **`HasOpenDropInSlot` computation (Matches side)**: derived from the Matches-owned rules — DropIn capacity is `drop_in_slots` plus (once the window is `Closed`) `released_drop_in_slots`, minus confirmed DropIn presences. Encapsulating this in Matches keeps the slot semantics inside their owning module; Geo treats the flag as opaque.
- **Boundaries**: Geo has its own read-only `GeoReadDbContext` mapping the `matches` table — this is the explicit ARCHITECTURE exception ("SELECT permission on `matches`"). It maps only the columns it needs and never `match_presences`, `waiting_list`, or any other module's table. The spatial query and the occupancy lookup are combined in `GetNearbyMatchesHandler` in application code — **not** as a database JOIN.
- **Schema ownership**: `matches` DDL is owned by Matches (F1.1). `GeoReadDbContext`'s configuration must mark the table as excluded from migrations (`builder.ToTable("matches", t => t.ExcludeFromMigrations())`) so Geo never emits or drifts the schema. Geo has no `Migrations/` folder and no design-time factory.
- **PostGIS translation**: with `Npgsql...NetTopologySuite`, `m.Location.IsWithinDistance(point, radiusMeters)` translates to `ST_DWithin(...)` and `m.Location.Distance(point)` to `ST_Distance(...)`, both returning meters because `location` is `geography`. The query point must carry `SRID = 4326`. The `ix_matches_location_gist` index services `ST_DWithin`.
- **Result cap**: to keep the payload bounded, the spatial query applies `Take(200)` after ordering by distance. With `radiusKm <= 50` and the GIST index this is a safe upper bound; if it is ever hit, the closest 200 are returned. Documented so behavior is deterministic; not exposed as a tunable in this spec.
- **Two-phase filtering caveat**: occupancy filtering happens after the spatial `Take`. This is acceptable because the radius already bounds the candidate set; a match dropped for having no open slots simply does not appear. No secondary fetch/backfill is performed.
- **`TimeProvider` injection**: register `TimeProvider.System` in `GeoModuleExtensions` via `TryAddSingleton`; use `TimeProvider.GetUtcNow()` for the `date_time > now` filter and in the validator if needed.
- **CancellationToken**: propagated through the controller action, handler, repository, and the `IMatchAvailabilityReader` call.
- **Controller thinness**: `MatchesMapController.GetNearby` binds the query record, runs the validator, calls the handler, returns `Ok(...)`; no business logic.
- **Serilog**: log `Lat`, `Lon`, `RadiusKm`, `OpenToDropIns`, and result `Count` at `Information`; do not log caller ID above `Debug`.
- **Route collision**: `MatchesMapController` uses route `api/v1/matches/nearby`; because `nearby` is a literal segment it does not collide with `GET /api/v1/matches/{id}` (F1.1) — the literal route wins over the `{id}` template in ASP.NET routing. Kept in the Geo module to preserve module ownership of the endpoint.
