# Spec: F2.3 — Group Ranking

## Origin
- User Story / Feature from SCOPE: F2.3 — Group Ranking
- Layer: 2
- Requested by: renanortega.dev@gmail.com

## Goal
Give every recurring match its own accumulated point ranking — each participant's total points earned inside that group (attendance, wins, MVPs) exposed as an ordered leaderboard through one endpoint — so a fixed group has a persistent competitive standing that no prior module produced.

## Primary module
`Quadra.Modules.Gamification`

> Rationale for a single primary module: SCOPE lists F2.3 solely under `Gamification`, and ARCHITECTURE assigns it the `group_rankings` and `point_transactions` own tables plus "Keeps the group ranking up to date". `Gamification` is the sole protagonist. Point *awarding* is performed asynchronously by `Quadra.Workers.Background` on the `MatchSummaryGenerated` signal (ARCHITECTURE data flow: "Background Worker calls `Gamification.DistributePoints(...)`"); the Worker is transport, not a co-author — it invokes a Gamification-owned write interface. `Matches` and `InGame` are read-only sources reached only through `Quadra.Shared.Contracts` interfaces. This mirrors the F2.1/F2.2 pattern (Worker writes, module owns the tables).

## Dependent modules (read-only via interface)
- `Quadra.Modules.Matches` — read-only, used **at HTTP read time** by the ranking endpoint to validate the match exists and is `Recurring`, and to resolve the grouping key + display name, via a new `IMatchGroupReader` interface declared in `Quadra.Shared.Contracts` and implemented in `Quadra.Modules.Matches`. Also used **by the Background Worker** to obtain the same descriptor when composing the write DTO. Never reads the `matches` table directly.
- `Quadra.Modules.InGame` — read-only, used **by the Background Worker only** to resolve each participant's team and win/loss outcome for a finished match, via the existing `IMatchResultReader.GetMatchResultAsync` (F1.6, `Quadra.Shared.Contracts`, implemented in InGame). Gamification's own HTTP surface never touches InGame.
- `Quadra.Modules.Auth` — the FA.1 JWT middleware populates `HttpContext.User` with the caller's `sub`; the ranking endpoint reads the claim (to compute `CallerEntry`), never the `users` table.
- `Quadra.Infrastructure` — provides the EF `DbContext` plumbing.

Gamification holds **no** `ProjectReference` to `Matches` or `InGame`. The cross-module reads happen either through `Quadra.Shared.Contracts` interfaces resolved via DI (read endpoint → `IMatchGroupReader`) or inside `Quadra.Workers.Background`, which composes a self-contained DTO before calling Gamification. Gamification itself only touches its own tables (`group_rankings`, `point_transactions`) plus the `IMatchGroupReader` read interface.

## Database changes

### New tables

#### `point_transactions`
The immutable, append-only ledger of every point award. It is both the audit trail and the idempotency guard for at-least-once SQS delivery — `group_rankings` is derived (recomputed) from it, never incremented blindly.
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` `uuid` `NOT NULL` — the awarded player; app-layer FK to `users.id`; no DDL FK (module boundary rule)
- `group_id` `uuid` `NOT NULL` — the grouping key; app-layer FK to the recurring `matches.id`. In the MVP `group_id == match_id` (SCOPE ruling), but the column is deliberately distinct so a future recurring-occurrence model can repoint it to a parent recurring-match id with no migration. No DDL FK.
- `match_id` `uuid` `NOT NULL` — the summarized match that triggered the award; app-layer FK to `matches.id`; no DDL FK
- `reason` `varchar(16)` `NOT NULL` — enum string: `Attendance | Win | Mvp`
- `points` `integer` `NOT NULL` — the point value for this reason (`10 | 15 | 25`)
- `match_date_time` `timestamptz` `NOT NULL` — snapshot of the triggering match's date/time; ordering key within a group
- `awarded_at` `timestamptz` `NOT NULL` — the summary's `GeneratedAt`
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`

**Constraints:**
- `UNIQUE (user_id, match_id, reason)` — each reason is awarded at most once per player per match; the idempotency key for redelivered `MatchSummaryGenerated`.

**Indexes:**
- unique btree on `(user_id, match_id, reason)`
- btree on `(group_id, user_id, match_date_time)` — per-group per-player history ordering
- btree on `(group_id, match_id)` — per-match cleanup / lookup

> No `updated_at` — a ledger row is immutable; it is inserted idempotently (ignore-on-conflict) and never mutated.

#### `group_rankings`
Materialized standing of one player inside one group. Recomputed from `point_transactions` on every finished match; this is what the read endpoint serves.
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `group_id` `uuid` `NOT NULL` — recurring `matches.id`; app-layer FK; no DDL FK. Kept distinct from `match_id` per SCOPE ruling.
- `user_id` `uuid` `NOT NULL` — app-layer FK to `users.id`; no DDL FK
- `total_points` `integer` `NOT NULL DEFAULT 0` — sum of this player's `point_transactions.points` for this `group_id`
- `matches_counted` `integer` `NOT NULL DEFAULT 0` — distinct summarized matches in the group this player attended (has an `Attendance` transaction for)
- `last_match_id` `uuid` `NULL` — most recent counted match
- `last_match_date_time` `timestamptz` `NULL` — most recent counted match's date/time
- `updated_at` `timestamptz` `NOT NULL DEFAULT now()`
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`

**Constraints:**
- `UNIQUE (group_id, user_id)` — one standing row per player per group.

**Indexes:**
- unique btree on `(group_id, user_id)`
- btree on `(group_id, total_points DESC, user_id)` — ranking ordering + deterministic tiebreak

### New columns in existing tables
None.

## REST endpoints

### `GET /api/v1/matches/{matchId}/ranking`
Returns the accumulated point ranking for a recurring match group, ordered by total points descending. `matchId` is the recurring match id, which in the MVP is the grouping key (`GroupId == matchId`, SCOPE ruling).
- **Auth**: JWT required (`[Authorize]`)
- **Request** (query): `page` (default `1`, min `1`), `pageSize` (default `20`, min `1`, max `50`)
- **Response 200 OK**: `GroupRankingResponse` (see below)
- **Possible errors**:
  - `400` — `page`/`pageSize` out of allowed range
  - `401` — missing or invalid JWT
  - `404` — no match exists for `matchId`
  - `409` — the match exists but is `OneOff` (group ranking is only defined for recurring matches per SCOPE)
- **Validation** (FluentValidation, `GroupRankingQueryValidator`): `Page >= 1`; `1 <= PageSize <= 50`.
- **Behavior**:
  1. Extract `callerId` from `User.FindFirst(ClaimTypes.NameIdentifier)?.Value`; return `401` if the claim is missing or not a `Guid`.
  2. Validate the query; on failure return `400`.
  3. Resolve the match via `IMatchGroupReader.GetMatchGroupAsync(matchId, ct)`; if `null` → `404`.
  4. If `descriptor.Type != "Recurring"` → `409 ConflictProblem("Group ranking is only available for recurring matches.")`.
  5. Use `groupId = descriptor.GroupId`. Query `IGroupRankingRepository.GetPageAsync(groupId, page, pageSize, ct)` ordered by `total_points DESC, user_id ASC` (deterministic tiebreak), plus the total row count for the group. `Rank` is the 1-based absolute position in that ordering (`(page-1)*pageSize + index + 1`).
  6. Query the caller's own standing via `IGroupRankingRepository.FindEntryAsync(groupId, callerId, ct)` and its absolute rank via `IGroupRankingRepository.GetRankAsync(groupId, callerId, ct)`; map to `CallerEntry` (may fall outside the returned page). `null` when the caller has no points in this group.
  7. Map → `GroupRankingResponse` → `200 OK`. An existing recurring match with no finished matches yet returns `200` with an empty `Items` list, `TotalCount = 0`, `CallerEntry = null`.

### Response records
```csharp
public sealed record GroupRankingResponse(
    Guid GroupId,                                   // == the recurring match id in the MVP
    string MatchName,
    IReadOnlyList<GroupRankingEntryResponse> Items,
    GroupRankingEntryResponse? CallerEntry,         // caller's own standing; may be outside the page; null if none
    int Page,
    int PageSize,
    long TotalCount,
    bool HasNextPage);

public sealed record GroupRankingEntryResponse(
    int Rank,                                       // 1-based absolute position; ties broken by UserId ascending
    Guid UserId,
    int TotalPoints,
    int MatchesCounted,
    DateTimeOffset? LastMatchDateTime);
```

## SQS events

### Published
None. Gamification is a points terminus in the MVP; it originates no events. (A future `PointsAwarded` for push notifications is deferred — the MVP has no declared consumer for it, so it is not introduced.)

### Consumed
Gamification does not host an SQS consumer itself. Per ARCHITECTURE ("Background Worker ... distribute XP, update rankings") the following event is consumed **inside `Quadra.Workers.Background`**, which invokes the Gamification-owned write interface:

- `MatchSummaryGenerated` (from `Quadra.Modules.Matches`, F1.6) — the **single authoritative "finished match" signal** for Gamification (the same event F2.1/F2.2 already consume). For a **Recurring** match only, the Worker composes a `FinishedMatchPoints` DTO (enriched via `IMatchGroupReader` for the group key + type, and `IMatchResultReader` for each participant's team + win/loss) and calls `IMatchPointsWriter.ApplyFinishedMatchPointsAsync(...)`. For a **OneOff** match the Worker composes nothing and awards no points. Idempotent (UNIQUE `user_id, match_id, reason`; recompute-not-increment).

> **Design decision (see Implementation notes):** all three point rules are driven off `MatchSummaryGenerated` (which already carries `MvpPlayerId`), **not** off separate `MatchEnded` / `MvpAwarded` events. This keeps a single authoritative write per finished match and avoids double counting — identical to F2.1's decision to derive MVP-received from the summary. ARCHITECTURE's per-event "DistributePoints" description is illustrative; F1.6 established `MatchSummaryGenerated` as the canonical completion signal and F2.1 already adopted it.

## Acceptance criteria (from SCOPE)

SCOPE F2.3 wording covered by these tests:
- "endpoint returning accumulated point ranking per recurring match"
- "scoring per product doc rules (attendance +10, win +15, MVP +25)"
- "OUT: city-wide ranking (Layer 3)"

- [ ] AC-1 (scoring): after `IMatchPointsWriter.ApplyFinishedMatchPointsAsync` processes a finished recurring match in which player `P` attended, was on the winning team, and is the MVP, `P`'s `group_rankings` row has `total_points = 50` (Attendance 10 + Win 15 + Mvp 25) and three `point_transactions` rows (`Attendance`, `Win`, `Mvp`) exist for `(P, matchId)`.
- [ ] AC-2 (attendance-only): a participant who attended but neither won nor was MVP has `total_points = 10` and exactly one `Attendance` transaction.
- [ ] AC-3 (win without MVP): a winning participant who is not MVP has `total_points = 25` (Attendance 10 + Win 15).
- [ ] AC-4 (ordering + tiebreak): `GET /api/v1/matches/{matchId}/ranking` on a recurring group returns `200` with `Items` ordered by `TotalPoints` descending; two players with equal `TotalPoints` appear ordered by `UserId` ascending, and their `Rank` values follow that same order.
- [ ] AC-5 (absolute rank): each `Items[i].Rank` equals `(Page-1)*PageSize + i + 1`.
- [ ] AC-6 (unknown match): `GET /api/v1/matches/{matchId}/ranking` with a `matchId` that has no `matches` row returns `404`.
- [ ] AC-7 (OneOff): `GET /api/v1/matches/{matchId}/ranking` where the match exists and is `OneOff` returns `409`; and no `point_transactions` / `group_rankings` rows are ever written for that match by the Worker.
- [ ] AC-8 (empty group): `GET /api/v1/matches/{matchId}/ranking` on an existing recurring match that has no finished matches yet returns `200` with `Items` empty, `TotalCount = 0`, `HasNextPage = false`, and `CallerEntry = null`.
- [ ] AC-9 (idempotency): applying the same `MatchSummaryGenerated` twice (redelivery) leaves each affected player's `TotalPoints`, `MatchesCounted`, and `point_transactions` row count unchanged versus a single delivery.
- [ ] AC-10 (pageSize lower bound): `GET .../ranking?page=1&pageSize=0` returns `400`.
- [ ] AC-11 (pageSize upper bound): `GET .../ranking?page=1&pageSize=51` returns `400`.
- [ ] AC-12 (page lower bound): `GET .../ranking?page=0&pageSize=20` returns `400`.
- [ ] AC-13 (HasNextPage true): a group with `TotalCount = 25` requested at `page=1&pageSize=20` returns `Items.Count = 20` and `HasNextPage = true`.
- [ ] AC-14 (HasNextPage false): the same group at `page=2&pageSize=20` returns `Items.Count = 5` and `HasNextPage = false`.
- [ ] AC-15 (caller outside page): when the caller ranks 25th in a 25-player group and requests `page=1&pageSize=20`, the caller is absent from `Items` but `CallerEntry` is populated with `Rank = 25` and the caller's correct `TotalPoints`.
- [ ] AC-16 (caller with no points): when the caller has no `group_rankings` row for the group, `CallerEntry = null` while `Items` still returns the ranked players.
- [ ] AC-17 (auth): `GET /api/v1/matches/{matchId}/ranking` with a missing or invalid JWT returns `401`.

## Out of scope (be explicit)
- **City-wide / global ranking** — explicitly OUT per SCOPE F2.3 (Layer 3). This spec ranks strictly within a single recurring match group.
- **`player_xp` lifetime accumulator** — cut from the MVP by SCOPE ruling (2026-07-03); its only consumer is the Layer-3 city-wide leaderboard. No `player_xp` table, entity, config, repository, registration, or recompute step is created. It re-enters scope with that Layer-3 feature.
- **3-consecutive-match streak +20** — deferred and cut by SCOPE ruling (2026-07-03); unreachable while a group is summarized at most once (F1.1 defers occurrence generation; F1.6 enforces `UNIQUE (match_id)`). No `StreakCalculator`, no `Streak` point reason, no `current_streak` column, no streak recompute — no dormant/dead code. It re-enters scope only with the recurring-occurrence model.
- **Group ranking for OneOff matches** — SCOPE scopes the ranking to recurring matches; the endpoint returns `409` for a OneOff match and the Worker awards no group-ranking points for OneOff matches.
- **"First match as DropIn in a new group: +5" rule** — present in PRODUCT's point list but **not** enumerated in SCOPE F2.3 (which is source of truth and lists only attendance/win/MVP). Not implemented. SCOPE notes PRODUCT should be reconciled when convenient.
- **Point allocation as a synchronous part of any HTTP request** — awarding is async in the Background Worker off `MatchSummaryGenerated` (ARCHITECTURE); the ranking endpoint is read-only.
- **Achievements / badges / levels** — Layer 3 (US 1.2) for achievements; player *level* is F2.1's `Profile` concern, not part of the ranking.
- **Manual point adjustment / admin correction** — no write endpoint; points derive from `MatchSummaryGenerated` only.
- **Emitting notifications on rank change** — no event is published; a `PointsAwarded`/notification path has no declared consumer in the MVP.
- **Recomputing points if underlying InGame/Matches data changed** — that data is immutable after the summary (F1.6); no recompute-from-source path exists beyond idempotent redelivery.

## Implementation notes

### Write-side contract (Gamification-owned, invoked by the Background Worker)
```csharp
public interface IMatchPointsWriter
{
    Task ApplyFinishedMatchPointsAsync(FinishedMatchPoints points, CancellationToken cancellationToken);
}

public sealed record FinishedMatchPoints(
    Guid MatchId,
    Guid GroupId,                 // grouping key; == MatchId in the MVP (SCOPE ruling)
    DateTimeOffset MatchDateTime,
    Guid? MvpPlayerId,
    IReadOnlyList<FinishedMatchPlayerPoints> Players,   // all participants who played
    DateTimeOffset FinishedAt);

public sealed record FinishedMatchPlayerPoints(
    Guid PlayerId,
    bool Won);                    // true when the player's team is the winning team
```
These live in `Quadra.Modules.Gamification.Abstractions`. The Background Worker references the Gamification module and resolves `IMatchPointsWriter` via DI — mirroring ARCHITECTURE's "Background Worker calls `Gamification.DistributePoints(...)`". Gamification never references `Matches`/`InGame`.

### Award mapping (per finished match)
For each `FinishedMatchPlayerPoints` in `Players`:
- **Attendance +10** — every participant (presence in `Players` means they played; the participant set comes from the InGame team rosters, i.e. players who showed up).
- **Win +15** — when `Won == true`.
- **Mvp +25** — for the single player whose id equals `MvpPlayerId` (when non-null).

### Idempotency / recompute-not-increment (mirrors F2.1)
`ApplyFinishedMatchPointsHandler`, in one transaction:
1. Insert the `Attendance`/`Win`/`Mvp` ledger rows via `AddIfAbsentAsync` (ON CONFLICT `(user_id, match_id, reason)` DO NOTHING) — redelivery inserts nothing new.
2. Recompute each affected player's `group_rankings` row: `total_points = SumByGroupUserAsync(groupId, userId)`, `matches_counted = count(distinct match_id with an Attendance row)`, `last_match_id` / `last_match_date_time` from the latest attended match. `UpsertAsync`.

Because standings are **summed from the immutable ledger** rather than incremented, an at-least-once redelivery of `MatchSummaryGenerated` produces no drift.

### Grouping model (settled — SCOPE ruling 2026-07-03)
`GroupId == matchId` for the MVP: the single recurring `matches` row *is* the group. `MatchGroupReader` returns `GroupId = matchId` for a recurring match. The `group_id` column is kept distinct from `match_id` across both tables so a future recurring-occurrence model can set `group_id` to the parent recurring-match id with no schema change. This is ratified in SCOPE and is not an open question.

### Read path (boundary-safe)
The ranking endpoint validates the match through `IMatchGroupReader` (Matches, read-only) and reads only Gamification-owned tables for the standings. No cross-module JOIN; no InGame access at read time.

### Other notes
- **`TimeProvider` injection**: register `TimeProvider.System` via `TryAddSingleton`; use `GetUtcNow()` for all `updated_at`/`created_at` values so tests control time.
- **CancellationToken**: propagated through every handler, repository, reader and worker method, sourced from `HttpContext.RequestAborted` (API) or the worker's stopping token.
- **Nullable reference types** enabled; nullable fields are exactly `group_rankings.last_match_id`, `group_rankings.last_match_date_time`, and `GroupRankingEntryResponse.LastMatchDateTime`.
- **Controller thinness**: `GroupRankingController` triggers validation, calls the handler, and maps `MatchNotFoundForRankingException → 404` / `RankingNotAvailableForOneOffException → 409` to ProblemDetails; no business logic.
- **Serilog**: log `GroupId`, `MatchId` and per-reason point totals at `Information` on a points application; never log the full player list above `Debug`.
- **Configuration fail-fast**: `AddGamificationModule` throws at startup if the module's Postgres connection is unresolved; the Worker fails fast if `Aws:Sqs:MatchSummaryGeneratedQueueUrl` is missing.
