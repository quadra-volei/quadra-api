# Decisions

Decisions taken while integrating the mobile app with the API without stopping to ask. Each
one is the recommended default; any of them can be reversed — say which and it gets redone.

Format: date · decision · why.

## 2026-10-06 — Block 1: matches (create, list, detail, presence, guests)

| # | Decision | Why |
| --- | --- | --- |
| 1 | **Anyone joins an open match by confirming** (`PUT /matches/{id}/presences/me` with `Confirmed` and no presence row yet creates one). Declining a match you are not in is still 404. | The mobile "Entrar na partida" button has no invitation step; before this, only players the organizer had pre-listed could confirm, and nothing created that list. |
| 2 | A player who joins **while the window is open is a Regular; after it closes, a DropIn** (the existing drop-in slots = `MaxPlayers − RegularSlots`). | Keeps the Regular/DropIn rules of F1.2 intact without asking the player to pick a type. |
| 3 | The mobile form has one "players" number, so the app sends **`regularSlots = maxPlayers`** (no reserved drop-in slots). | The form has no drop-in field. The API still accepts a smaller `regularSlots`. |
| 4 | The confirmation window can be sent as **`confirmationOpensHoursBefore` (1–168)**: opens N hours before the start and **closes at the start**. The explicit `windowOpensAt/windowClosesAt` form still works; exactly one of the two. | That is what the mobile form collects (48/24/12/6 h). |
| 5 | **The window opens and closes by the clock**, not by a worker: every request that touches a match syncs it first, and an in-process sweeper (`Matches:WindowSweepSeconds`, default 60, 0 = off) covers matches nobody is looking at. A match whose window is already due is created `Open`. | There is no worker process on the free hosting; the manual open/close endpoints remain. On Render's free plan the service sleeps, so the sweep alone is not enough — hence the sync on request. |
| 6 | **Guests without an account** are rows in a new `match_guests` table (name + optional position), added/removed only by the organizer. They count as confirmed, against `MaxPlayers` and against the Regular slots; adding one to a full match is 409. | Approved for the MVP. A separate table keeps `match_presences.player_id` a real user id. |
| 7 | Guests are **not yet in team draft, scoreboard stats or MVP voting**. | Those are InGame concerns; handled in block 3. |
| 8 | **Private matches**: `visibility = Private` needs `inviteMode` = `Code` (an 8-character code generated by the API) or `Guests` (only the organizer puts people in). They never appear in `/matches/nearby`. The code is returned only in the organizer's detail, never in lists. | Mirrors the two options of the mobile form. Not listing them is the meaning of private. |
| 9 | `/matches/nearby` now also lists **`Draft`** matches (window not open yet) and returns `confirmedCount`, `format`, `level`. | A match created today for next week must be findable on the map before its window opens. |
| 10 | **Multi-day recurrence** is stored as `recurrenceDays` (ISO 1–7). `dayOfWeek` is kept and, when omitted, is the first of those days. No future occurrences are generated. | The mobile form allows several days. Generating occurrences is a separate feature (not in the MVP list). |
| 11 | `format` (`2X2/4X4/6X6`), `level`, `durationMinutes`, `priceMonthly` are **optional, descriptive columns**; nothing enforces them (e.g. `6X6` does not force 12 players). | They exist for display and filters; closes pending refactor R1. Cover image stays out: it is not in the create contract. |
| 12 | Player identities in rosters come from Profile through **`IPlayerSummaryReader`** (Shared). A player with no profile shows as "Player". | Module boundary rule: Matches must not read Profile tables. |
| 13 | New read endpoints instead of changing existing ones: **`GET /matches/mine`** (matches I organize or joined, from 6 h ago onwards, soonest first) and **`GET /matches/{id}/detail`** (match + organizer + roster + guests + waiting list + my standing). | Existing `GET /matches` and `GET /matches/{id}` keep their contracts and tests. The 6 h grace keeps a match that is being played on the home screen. |

## 2026-10-06 — Block 3: in-game (teams, live scoreboard, MVP, summary)

The app plays a pickup game ("racha") with **2 to 4 teams** where each set is played by two of
them; the backend only knew two fixed teams. The backend followed the app.

| # | Decision | Why |
| --- | --- | --- |
| 20 | **Teams: 2 to 4** (`POST /teams/draft` body `{teamCount, perTeam, mode}`), named Team A…D. `mode` is `Balanced` (snake draft by level, default) or `Random`. With `perTeam` and more players than slots, who sits out is random. No body = the previous behaviour (two balanced teams). | Matches the team-count / per-team / draw-mode controls of the app. A random bench is the only choice that does not always exclude the weakest. |
| 21 | **Guests are drawn into the teams** (`isGuest` on the member), counted as Beginner. They are left out of everything that needs an account: `TeamsFormed`, MVP voting (cannot vote or be voted), summary participants, stats and ranking. | A guest fills a slot on court; they have no profile to rate or reward. |
| 22 | Teams can be drawn and the scoreboard created while the match is **Open or Closed** (before: only Closed). A game played while confirmations were still open can be ended and summarized. | The window closes at the start time; organizers draw teams some minutes before. |
| 23 | **Each set records the pair that played it.** With two teams nothing changes (the next set opens by itself). With more than two (`rotatesTeams`), after a set the game waits (`awaitingNextSet`) until the organizer picks the next pair: `POST /scoreboard/sets {teamAId, teamBId}`. The first pair is chosen when the scoreboard is created. | "Winner stays, next team comes in" — the S13.5 screen of the app. |
| 24 | With rotating teams the game ends when **any team reaches the sets of the format** (2 in best of 3), whoever it beat; the deciding set (to 15) is a set between two teams that are both one win away. Ending the game by hand gives it to the team with the most sets (tie = no winner). | The natural generalization: with two teams it is exactly the previous rule. |
| 25 | **End a set early** — `POST /scoreboard/sets/{n}/end`: whoever is ahead takes it (a tie cannot be ended). | Pickup games play shorter sets (to 15, by time). This avoids configuring a target per match. |
| 26 | **Undo** — `DELETE /scoreboard/sets/{n}/points/last`: takes back the last point only, one level, and never a point that already closed the set. | Fixes a mis-tap without keeping a point-by-point history. Ceiling: a mis-tap on set point cannot be undone. |
| 27 | **MVP voting opens by itself when the game ends** (24 h deadline). The manual open endpoint still exists and answers 409 when the voting is already there. | The app has no "open voting" step; players go straight from the final point to the vote. |
| 28 | **Live updates: SignalR hub at `/hubs/match`** (`JoinMatchRoom` / `LeaveMatchRoom`, events `ScoreboardUpdated` / `PresenceUpdated`), **without Redis**: groups live in the memory of the single API instance. | Asked for; the free hosting runs one instance. Add the Redis backplane before running more than one. |
| 29 | `GET /matches/{id}/detail` now carries `game` (`scoreboardState`, `mvpVotingState`, `hasSummary`). | One request tells the app which screen comes next (live scoreboard, vote, summary). |
| 30 | The **summary of a game with rotating teams** keeps the existing shape: winner, MVP, teams and the sets with their points — but not which pair played each set, and the "sets won" pair shown is the last pair on court. | Extending the stored summary needs its own migration and screen design; the result (who won, stats, ranking) is already correct. |

## 2026-10-14 — Friends' activity, level numbers

| # | Decision | Why |
| --- | --- | --- |
| 57 | **A player has a level number from accumulated points** (Johny's ruling, revisits the 2026-07-03 cut of a lifetime accumulator): points = attendance +10 per finished match, win +15, MVP +25, over every finished match in the player's history (one-off matches included; the group ranking still gives one-offs no points). ## 2026-10-15 — A recurring group goes on

| # | Decision | Why |
| --- | --- | --- |
| 64 | **Generating a recurring game's summary creates the group's next game** (ends the 2026-07-03 ruling #32). `matches.group_id` (null on the first game and on one-offs) points every later game at the **group = the id of its first game**; `IMatchGroupReader` returns it, so the point ledger and `group_rankings` add up over every game of the group. The next game copies the finished one (organizer, name, description, place, slots, prices, format, level, duration, visibility, invite mode **and invite code**, cover, frequency and week days) on the next of its week days, in Brasília time, at the same clock time; when that day falls in a later week it moves 1 (weekly), 2 (biweekly) or 4 (monthly) weeks on, rolled forward until it is in the future. Its confirmation window keeps the old distance to the game but never opens before now. Everyone who had **confirmed** the finished game gets a **Pending** presence of the same type (they confirm again; a private game stays visible to them); guests and the waiting list do not carry over. `MatchCreated` is published and a due window opens at once.
