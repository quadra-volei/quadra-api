# Spec: F2.1 — Player Profile

## Origin
- User Story / Feature from SCOPE: F2.1 — Player Profile
- Layer: 2
- Requested by: renanortega.dev@gmail.com

## Goal
Give every player a persistent identity — photo, name, positions, an automatically derived skill level, accumulated match stats and a paginated match history — all derived from match events and readable through the API, so the app can show a player card that was impossible before this module existed.

## Primary module
`Quadra.Modules.Profile`

> Rationale for a single primary module: SCOPE lists F2.1 solely under `Profile`. Writes are performed asynchronously by `Quadra.Workers.Background` (per ARCHITECTURE: "Read-heavy — Background Worker writes, the app reads" and the "player voted MVP" data flow where the Background Worker calls `Profile.UpdateStats(playerId)`). The Background Worker is not a co-author of this feature; it is the transport that invokes Profile-owned write interfaces. Other modules (`Auth`, `Matches`, `InGame`) are read-only sources reached through `Quadra.Shared.Contracts` interfaces.

## Dependent modules (read-only via interface)
- `Quadra.Modules.Auth` — the FA.1 JWT middleware populates `HttpContext.User` with the caller's `sub`; every read/update endpoint reads the claim, never the `users` table. The `UserRegistered` event (FA.2, `Quadra.Shared.Events.Auth`) bootstraps an empty profile.
- `Quadra.Modules.Matches` — read-only, consumed **by the Background Worker** (not by Profile's HTTP surface) to enrich a finished match with its `name` and `dateTime`, via a new `IMatchDescriptorReader` interface declared in `Quadra.Shared.Contracts` and implemented in `Quadra.Modules.Matches`.
- `Quadra.Modules.InGame` — read-only, consumed **by the Background Worker** to resolve each participant's team and win/loss outcome, via the existing `IMatchResultReader.GetMatchResultAsync` (F1.6, `Quadra.Shared.Contracts`, implemented in InGame).
- `Quadra.Infrastructure` — provides `IEventPublisher` (unused here — Profile publishes nothing in MVP), the EF `DbContext` plumbing, and a new S3 photo-storage abstraction (`IProfilePhotoStorage`) for presigned upload/read URLs.

Profile holds **no** `ProjectReference` to `Matches` or `InGame`. The cross-module reads above happen inside `Quadra.Workers.Background`, which references the module interface implementations and composes a self-contained DTO before calling Profile. Profile itself only touches its own tables plus the `IProfilePhotoStorage` abstraction.

## Database changes

### New tables

#### `player_profiles`
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` `uuid` `NOT NULL UNIQUE` — app-layer FK to `users.id`; no DDL FK (module boundary rule). One profile per user.
- `display_name` `varchar(80)` `NOT NULL` — the player's name (SCOPE "name"). Seeded with a system placeholder (`'Player'`) at provisioning because signup (FA.2) carries no name; the user sets it via `PUT /profiles/me`.
- `primary_position` `varchar(24)` `NULL` — enum string: `Setter | OutsideHitter | Opposite | MiddleBlocker | Libero` (see Open questions #4 on the position catalog)
- `secondary_position` `varchar(24)` `NULL` — same enum; must differ from `primary_position` when both set
- `photo_object_key` `varchar(512)` `NULL` — S3 object key (the "photo (S3 object reference)"); `NULL` when no photo uploaded
- `level` `varchar(16)` `NOT NULL DEFAULT 'Beginner'` — derived, never client-set. MVP-producible values: `Beginner | Intermediate` (string column; Advanced/Elite added when those tiers are activated, no migration needed)
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`
- `updated_at` `timestamptz` `NOT NULL DEFAULT now()`

**Indexes:** unique btree on `user_id`.

#### `player_stats`
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` `uuid` `NOT NULL UNIQUE` — app-layer FK to `users.id`; no DDL FK
- `matches_played` `integer` `NOT NULL DEFAULT 0`
- `wins` `integer` `NOT NULL DEFAULT 0`
- `losses` `integer` `NOT NULL DEFAULT 0`
- `draws` `integer` `NOT NULL DEFAULT 0` — matches ended level (F1.6 allows a null winner)
- `mvps_received` `integer` `NOT NULL DEFAULT 0`
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`
- `updated_at` `timestamptz` `NOT NULL DEFAULT now()`

**Indexes:** unique btree on `user_id`.

> `player_stats` is a separate table from `player_profiles` per ARCHITECTURE ("Own tables: `player_profiles`, `player_stats`, `player_cards`"). `player_cards` is **F2.2** and is out of scope here.

#### `player_match_history`
Realizes the "match history" responsibility listed for the Profile module in ARCHITECTURE. Each row is one player's snapshot of one finished match.
- `id` `uuid` `PRIMARY KEY DEFAULT gen_random_uuid()`
- `user_id` `uuid` `NOT NULL` — the player this row belongs to; app-layer FK to `users.id`
- `match_id` `uuid` `NOT NULL` — app-layer FK to `matches.id`; no DDL FK
- `match_name` `varchar(120)` `NOT NULL` — snapshot (from `IMatchDescriptorReader`)
- `match_date_time` `timestamptz` `NOT NULL` — snapshot of when the match happened
- `team_id` `uuid` `NULL` — the team the player was on (snapshot); app-layer FK to `teams.id`
- `outcome` `varchar(8)` `NOT NULL` — enum string: `Win | Loss | Draw`
- `was_mvp` `boolean` `NOT NULL DEFAULT false`
- `duration_seconds` `integer` `NULL`
- `recorded_at` `timestamptz` `NOT NULL` — the summary's `GeneratedAt`
- `created_at` `timestamptz` `NOT NULL DEFAULT now()`

**Constraints:** `UNIQUE (user_id, match_id)` — a match appears once per player; the idempotency guard for at-least-once SQS delivery.

**Indexes:**
- unique btree on `(user_id, match_id)`
- btree on `(user_id, match_date_time DESC)` — pagination ordering
- btree on `match_id`

> No `updated_at` — a history row is a snapshot; it is upserted idempotently (see Implementation notes) but not semantically mutated after the match is recorded.

## REST endpoints

### `GET /api/v1/profiles/me`
Returns the authenticated caller's own profile, stats and level.
- **Auth**: JWT required (`[Authorize]`)
- **Request**: no body
- **Response 200 OK**: `PlayerProfileResponse` (see below)
- **Possible errors**:
  - `401` — missing or invalid JWT
  - `404` — no profile exists yet for the caller (should not occur once the `UserRegistered` provisioning has run; returned defensively)
- **Behavior**:
  1. Extract `callerId` from `User.FindFirst(ClaimTypes.NameIdentifier)?.Value`; return `401` if parse fails.
  2. Load via `IPlayerProfileRepository.FindByUserIdAsync(callerId, ct)` (profile + stats); return `404` if missing.
  3. If `photo_object_key` is set, resolve a short-lived read URL via `IProfilePhotoStorage.GetReadUrlAsync(objectKey, ct)`; else `PhotoUrl = null`.
  4. Map → `PlayerProfileResponse` → `200 OK`.

### `GET /api/v1/profiles/{userId}`
Returns another player's profile (public within the app — no private fields exist on a profile).
- **Auth**: JWT required (`[Authorize]`)
- **Request**: no body
- **Response 200 OK**: `PlayerProfileResponse`
- **Possible errors**:
  - `401` — missing or invalid JWT
  - `404` — no profile exists for `userId`
- **Behavior**: identical to `GET /profiles/me` but keyed on the route `userId`.

### `PUT /api/v1/profiles/me`
Updates the caller's editable profile fields. Stats and level are **not** editable here (SCOPE OUT: manual stat editing).
- **Auth**: JWT required (`[Authorize]`)
- **Request** (C# record):
  ```csharp
  public record UpdateProfileRequest(
      string DisplayName,
      string? PrimaryPosition,      // null clears; else one of the position enum values
      string? SecondaryPosition,
      string? PhotoObjectKey);      // the object key previously returned by the upload-url endpoint; null clears the photo
  ```
- **Response 200 OK**: `PlayerProfileResponse` (updated)
- **Possible errors**:
  - `400` — validation failure
  - `401` — missing or invalid JWT
  - `404` — caller has no profile
- **Validation** (FluentValidation, `UpdateProfileRequestValidator`):
  - `DisplayName`: required, trimmed, length 2..80.
  - `PrimaryPosition`: when non-null, must be one of `Setter | OutsideHitter | Opposite | MiddleBlocker | Libero`.
  - `SecondaryPosition`: when non-null, must be a valid position AND must differ from `PrimaryPosition`.
  - `SecondaryPosition` may only be set when `PrimaryPosition` is set (no secondary without a primary).
  - `PhotoObjectKey`: when non-null, must match the owned-key prefix `profiles/{callerId}/` and be ≤ 512 chars (prevents pointing the reference at another user's object).
- **Behavior**:
  1. Extract `callerId`; return `401` if parse fails.
  2. Validate the request; on failure return `400`.
  3. Load the profile via `IPlayerProfileRepository.FindByUserIdAsync(callerId, ct)`; return `404` if missing.
  4. Apply `profile.UpdateDetails(displayName, primaryPosition, secondaryPosition, photoObjectKey, now)` (bumps `updated_at`). Level and stats are untouched.
  5. Persist via `IPlayerProfileRepository.UpdateAsync(profile, ct)`.
  6. Resolve the photo read URL (as in `GET`) and map → `PlayerProfileResponse` → `200 OK`.

### `POST /api/v1/profiles/me/photo/upload-url`
Issues a short-lived presigned S3 `PUT` URL so the client uploads the photo bytes directly to S3 (the API is never in the binary path). The client then calls `PUT /profiles/me` with the returned `objectKey` to persist the reference.
- **Auth**: JWT required (`[Authorize]`)
- **Request** (C# record):
  ```csharp
  public record PhotoUploadUrlRequest(
      string ContentType);          // "image/jpeg" | "image/png" | "image/webp"
  ```
- **Response 201 Created**:
  ```csharp
  public record PhotoUploadUrlResponse(
      string UploadUrl,             // presigned S3 PUT URL
      string ObjectKey,             // "profiles/{callerId}/photo/{guid}.<ext>"
      DateTimeOffset ExpiresAt);
  ```
- **Possible errors**:
  - `400` — unsupported `ContentType`
  - `401` — missing or invalid JWT
- **Validation** (FluentValidation, `PhotoUploadUrlRequestValidator`):
  - `ContentType`: required; one of `image/jpeg`, `image/png`, `image/webp`.
- **Behavior**:
  1. Extract `callerId`; return `401` if parse fails.
  2. Validate; on failure `400`.
  3. Compute `objectKey = $"profiles/{callerId}/photo/{Guid.NewGuid()}.{ext}"` (ext derived from content type).
  4. Call `IProfilePhotoStorage.CreateUploadUrlAsync(objectKey, contentType, ct)` → `(uploadUrl, expiresAt)`.
  5. Return `201 Created` with `PhotoUploadUrlResponse`. Persisting the reference happens in `PUT /profiles/me`.

### `GET /api/v1/profiles/me/match-history`
Returns the caller's match history, newest first, paginated.
- **Auth**: JWT required (`[Authorize]`)
- **Request** (query): `page` (default `1`, min `1`), `pageSize` (default `20`, min `1`, max `50`)
- **Response 200 OK**: `PagedResponse<MatchHistoryEntryResponse>`
- **Possible errors**:
  - `400` — `page` or `pageSize` out of allowed range
  - `401` — missing or invalid JWT
- **Validation** (FluentValidation, `MatchHistoryQueryValidator`): `Page >= 1`; `1 <= PageSize <= 50`.
- **Behavior**:
  1. Extract `callerId`; return `401` if parse fails.
  2. Validate query; on failure `400`.
  3. Query `IPlayerMatchHistoryRepository.GetPageAsync(callerId, page, pageSize, ct)` ordered by `match_date_time DESC, match_id DESC` (stable tiebreak), plus a total count.
  4. Map → `PagedResponse<MatchHistoryEntryResponse>` (`HasNextPage = page * pageSize < totalCount`) → `200 OK`.

### `GET /api/v1/profiles/{userId}/match-history`
Same as above, keyed on route `userId`. Same auth, validation, errors (`404` if no profile exists for `userId`).

## SQS events

### Published
None. Profile is a read/stat-store terminus in the MVP; it does not originate events.

### Consumed
Profile does not host an SQS consumer itself. Per ARCHITECTURE ("Read-heavy — Background Worker writes") the following events are consumed **inside `Quadra.Workers.Background`**, which then invokes Profile-owned write interfaces:

- `UserRegistered` (from `Quadra.Modules.Auth`, FA.2) — the Worker calls `IPlayerProfileProvisioner.EnsureProfileAsync(userId, ct)` to bootstrap an empty `player_profiles` + `player_stats` pair. Idempotent (UNIQUE `user_id`).
- `MatchSummaryGenerated` (from `Quadra.Modules.Matches`, F1.6) — the **single authoritative "finished match" signal** for Profile. For each `ParticipantPlayerId` the Worker composes a `FinishedMatchParticipation` (enriched via `IMatchDescriptorReader` for name/date and `IMatchResultReader` for team + outcome + `was_mvp` derived from `MvpPlayerId`) and calls `IPlayerStatsWriter.ApplyFinishedMatchAsync(...)`. Idempotent (UNIQUE `user_id, match_id`).

> Design decision (see Implementation notes): Profile derives MVP-received from `MatchSummaryGenerated.MvpPlayerId`, **not** from `MvpAwarded`, to keep a single write per finished match and avoid double counting. F1.6 requires MVP voting to be closed before the summary is generated, so `MvpPlayerId` is already decided when the summary event fires.

## Acceptance criteria (from SCOPE, as amended)
- [ ] photo (S3 object reference), name, primary position, secondary position — position catalog `Setter | OutsideHitter | Opposite | MiddleBlocker | Libero`
- [ ] automatically calculated level — **MVP scope: `Beginner` and `Intermediate` only**. `Beginner` when `matches_played < 10`; `Intermediate` when `matches_played >= 10 && mvps_received >= 1`. `Advanced`/`Elite` deferred (SCOPE/PRODUCT amended); a player above those thresholds remains `Intermediate`.
- [ ] aggregated stats: matches played, wins, losses, draws, MVPs received (`frequency` deferred — cut from MVP per amended SCOPE)
- [ ] match history with pagination
- [ ] OUT: manual stat editing (everything derived from events)

## Out of scope (be explicit)
- **Manual stat editing** — explicitly OUT per SCOPE F2.1; stats and level are derived from `MatchSummaryGenerated` only, never client-writable. `PUT /profiles/me` touches display name, positions and photo reference exclusively.
- **Player Card data / free-premium flag** — F2.2 (`player_cards` table, "generated after 3 recorded matches"). Not created here.
- **Group ranking / points / XP** — F2.3 and `Gamification`; the profile shows no point totals.
- **Visual rendering of the profile or card** — frontend; this spec returns JSON and S3 URLs only.
- **Player search by level/position/region** — Layer 3, REJECTED.
- **Player rating / peer reviews** — Layer 3 (US 3.3), REJECTED.
- **Advanced per-play stats (serve/block/attack/defense)** — Layer 3, REJECTED.
- **Achievements / badges** — Layer 3 (US 1.2), REJECTED.
- **Profile of matches that never reached `MatchSummaryGenerated`** — only summarized (finished) matches enter history/stats.
- **Direct SQS consumption inside the Profile module** — consumption lives in `Quadra.Workers.Background`; Profile exposes write interfaces only.
- **Image validation / resizing / moderation of uploaded photos** — not in SCOPE; the API only stores the S3 reference.

## Implementation notes

### Resolved decisions (human-approved, docs amended)
The SCOPE/PRODUCT gaps flagged during scope audit were resolved by the human on 2026-07-02. `docs/SCOPE.md` (F2.1), `docs/PRODUCT.md` (level table) and `docs/ARCHITECTURE.md` (Profile own tables) were amended to match. This spec is now fully specified and implementable.

1. **Level tiers — MVP computes `Beginner` and `Intermediate` only.**
   - `Beginner` when `matches_played < 10`.
   - `Intermediate` when `matches_played >= 10 && mvps_received >= 1`.
   - `Advanced` (needs an undefined "vote average" + per-player MVP-vote data no event carries) and `Elite` (needs the Layer-3 global ranking) are **deferred**. `PlayerLevelCalculator` implements the two tiers above and nothing else; a player exceeding the Advanced/Elite thresholds stays `Intermediate`. The `PlayerLevel` enum declares only the two MVP-producible values (`Beginner`, `Intermediate`); `Advanced`/`Elite` are added when their tiers are activated. Because `level` is a `varchar(16)` string column, no migration is needed then. `PRODUCT.md` level table updated with an "MVP status" column.
2. **`frequency` stat — cut from the MVP.** No formula is defined in PRODUCT/SCOPE. The column and `PlayerStatsResponse.Frequency` field are removed entirely (not parked as null). `SCOPE.md` F2.1 records it as deferred, to be re-added when a formula exists. The related `attended` history column is also removed (its only consumer was `frequency`).
3. **Position catalog — the standard 5.** `Setter | OutsideHitter | Opposite | MiddleBlocker | Libero`, locked into the `PlayerPosition` enum, the `player_profiles` columns and `UpdateProfileRequestValidator`. Enumerated in `SCOPE.md` F2.1.
4. **Draws — kept.** F1.6 permits a null-winner match, so `Draw` is a reachable outcome; the `draws` stat, the `Draw` outcome branch and the null-winner mapping in the Background Worker are retained. `draws` added to the `SCOPE.md` F2.1 stat list.

### Write-side contract (Profile-owned, invoked by the Background Worker)

```csharp
    Guid MatchId,

    DateTimeOffset MatchDateTime,
    Guid? TeamId,

    DateTimeOffset FinishedAt);
```
- These live in `Quadra.Modules.Profile.Abstractions`. The Background Worker references the Profile module and resolves them via DI — mirroring ARCHITECTURE's "Background Worker calls `Profile.UpdateStats(playerId)`". The Profile module never references `Matches`/`InGame`.
- **Idempotency / recompute-not-increment**: `ApplyFinishedMatchHandler` (a) upserts the `player_match_history` row on `(user_id, match_id)`; (b) **recomputes** `player_stats` from the history rows (`GetOutcomeCountsAsync`) rather than incrementing counters — so a redelivered `MatchSummaryGenerated` (at-least-once SQS) produces no drift; (c) recomputes `level` via `PlayerLevelCalculator`; (d) commits all three in one transaction.
- `EnsureProfileAsync` is a no-op when the profile already exists (UNIQUE `user_id` + existence check), covering `UserRegistered` redelivery.

### Background Worker composition (boundary-safe)
For each `ParticipantPlayerId` in `MatchSummaryGenerated`:
1. `IMatchDescriptorReader.GetMatchDescriptorAsync(matchId)` → `name`, `dateTime` (Matches, read-only).
2. `IMatchResultReader.GetMatchResultAsync(matchId)` (F1.6, InGame) → the player's `teamId` and the `winnerTeamId`. Outcome = `Win` if `teamId == winnerTeamId`; `Draw` if `winnerTeamId == null`; else `Loss`.
3. `wasMvp = (summary.MvpPlayerId == playerId)`; `durationSeconds = summary.DurationSeconds`; `finishedAt = summary.GeneratedAt`.
4. Call `IPlayerStatsWriter.ApplyFinishedMatchAsync(...)`.

This keeps all cross-module reads inside the Worker; Profile receives a self-contained DTO and touches only its own tables (module boundary satisfied).

### Other notes
- **`IPlayerLevelReader` upgrade**: registering the real `PlayerLevelReader` (F2.1) overrides the F1.3 `NoOpPlayerLevelReader`, so team drafting immediately balances on real levels. Because the reader returns the persisted `player_profiles.level` string, it must be resilient to players who have no profile yet (return `"Beginner"` for unknown IDs).
- **Photo URLs**: upload via presigned S3 PUT (client → S3 directly, API out of the byte path); read via short-lived presigned GET resolved at response time. CloudFront/CDN optimization of the read path is out of scope. TTLs come from `Aws:S3` config.
- **`PhotoObjectKey` ownership check**: `UpdateProfileRequestValidator` requires the key to start with `profiles/{callerId}/`, preventing a caller from referencing another user's object.
- **Manual-edit boundary**: no endpoint mutates stats, level or history; SCOPE's "OUT: manual stat editing" is enforced structurally (no such route, no such repository method).
- **`TimeProvider` injection**: register `TimeProvider.System` via `TryAddSingleton` in `ProfileModuleExtensions`; use `GetUtcNow()` for all `now`/`updated_at` values so tests control time.
- **CancellationToken**: propagated through every handler, repository, reader, storage and worker method, sourced from `HttpContext.RequestAborted` (API) or the worker's stopping token.
- **Nullable reference types** enabled; nullable fields on entities are exactly `primary_position`, `secondary_position`, `photo_object_key`, `team_id`, `duration_seconds`.
- **Controller thinness**: `ProfilesController` triggers validation, calls the handler and maps exceptions to ProblemDetails; no business logic.
- **Serilog**: log `UserId` and `OutcomeCategory` on profile updates and finished-match application at `Information`; never log photo object keys above `Debug`; never log another player's data beyond the requested `userId`.
- **Configuration fail-fast**: `AddProfileModule` throws at startup if `Aws:S3:ProfilePhotosBucket` is missing; the Worker fails fast if its consumed queue URLs are missing.
